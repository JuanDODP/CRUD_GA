1. Visión General de la Arquitectura

Diagrama de capas, puertos activos y flujo de datos del sistema

El Sistema CRUDGA está compuesto por tres capas independientes que trabajan en conjunto. Cada capa tiene su propio repositorio, proceso de instalación y puerto de red. Comprender esta arquitectura antes de instalar garantiza una configuración correcta.

1.1 Diagrama de Capas

🌐

Frontend

Angular 21 + TailwindCSS + DaisyUI
Puerto: 4200

🪺

Backend API

NestJS sobre Node.js
Puerto: 3000

🗄️

Base de Datos

SQL Server 2022 (Docker)
Puerto: 1433

ℹ️
Repositorios separados

El Frontend y el Backend son repositorios Git distintos. Cada uno debe clonarse, configurarse y ejecutarse por separado. La base de datos se levanta con Docker desde el directorio del Backend.

1.2 Puertos y Servicios

:4200
Frontend AngularInterfaz de usuario — acceso desde el navegador en http://localhost:4200
:3000
Backend NestJS (API REST)Endpoints de datos — consumido por el Frontend
:1433
SQL Server 2022 (Docker)Motor de base de datos — consumido únicamente por el Backend

1.3 Flujo de Datos

El navegador del usuario se comunica exclusivamente con el Frontend. El Frontend envía peticiones HTTP al Backend. El Backend es el único que accede a la base de datos. Ningún componente externo se conecta directamente al puerto 1433 en producción.

FLUJO # Navegador → Frontend → Backend → Base de Datos

Usuario (browser)
  └─▶ Angular :4200    # Renderiza la UI
       └─▶ NestJS :3000    # Lógica de negocio / API REST
             └─▶ MSSQL :1433    # Persistencia — contenedor Docker

3. Instalación de Herramientas Base

Node.js, Docker Desktop y DataGrip — instalar una única vez

3.1 Node.js y npm

Node.js es el runtime de JavaScript requerido tanto para el Backend (NestJS) como para las herramientas de compilación del Frontend (Angular CLI). Se recomienda instalar la versión LTS más reciente (20.x o superior).

📦 Instalación con nvm (recomendado)

nvm (Node Version Manager) permite tener múltiples versiones de Node.js y cambiar entre ellas sin conflictos. Es la forma recomendada para entornos de desarrollo.

macOS / Linux — Terminal # 1. Instalar nvm
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.40.1/install.sh | bash

# 2. Reiniciar la terminal o ejecutar:
source ~/.zshrc

# 3. Instalar Node.js LTS
nvm install --lts
nvm use --lts

# 4. Verificar instalación
node --version # Debe mostrar v20.x.x o superior
npm --version # Debe mostrar 10.x.x o superior
💻 Instalación directa (Windows)

Descarga el instalador oficial desde nodejs.org → sección "Downloads" → selecciona la versión LTS → ejecuta el instalador .msi y sigue los pasos. Asegúrate de marcar la opción "Add to PATH".

✅
Verificación exitosa

Al ejecutar node --version en la terminal debe aparecer v20.x.x o superior. Si ves v18.x.x también es válido, pero se recomienda actualizar.

3.2 Docker Desktop

Docker Desktop es la plataforma de contenedores que permite ejecutar SQL Server en un entorno aislado sin instalarlo directamente en el sistema operativo. Es el método recomendado para desarrollo local.

  • Descargar Docker Desktop

    Visita docker.com/products/docker-desktop y descarga la versión correspondiente a tu sistema operativo (Mac Intel / Mac Apple Silicon / Windows).

  • Ejecutar el instalador

    En macOS: arrastra Docker.app a la carpeta Aplicaciones y ábrelo. En Windows: ejecuta el instalador .exe y acepta los permisos de administrador.

  • Iniciar Docker Desktop

    Abre la aplicación. Espera hasta que el ícono de la ballena en la barra de menú (macOS) o la bandeja del sistema (Windows) muestre el estado "Docker is running".

  • Configurar recursos (recomendado)

    En Docker Desktop → Settings → Resources → Memory: asigna al menos 4 GB de RAM para que SQL Server funcione correctamente.

  • Verificar instalación

    En una terminal, ejecuta docker --version. Debe mostrar Docker version 24.x.x o superior.

VERIFICACIÓN docker --version
Docker version 27.x.x, build xxxxxxx

docker compose version
Docker Compose version v2.x.x

3.3 DataGrip (Cliente SQL)

DataGrip es el IDE de JetBrains para bases de datos. Permite conectarse al contenedor Docker de SQL Server, explorar tablas, ejecutar consultas y crear la base de datos inicial de forma visual.

  • Descargar DataGrip

    Visita jetbrains.com/datagrip y descarga la versión de prueba (30 días gratuitos) o activa tu licencia de JetBrains/estudiante.

  • Instalar y abrir

    Ejecuta el instalador y sigue los pasos. Al abrirlo por primera vez, selecciona el tema de interfaz de tu preferencia.

  • Nueva conexión a SQL Server

    En el panel Database → + → Data Source → Microsoft SQL Server. Los datos de conexión se configuran en la Sección 4.4.

💡
Alternativas gratuitas a DataGrip

Azure Data Studio (gratis, de Microsoft, recomendado para Windows) o TablePlus (versión gratuita con funcionalidad suficiente para desarrollo) son excelentes opciones sin costo.

4. Configuración de la Base de Datos

SQL Server 2022 en Docker · Variables de entorno · Creación de la BD

4.1 Levantar SQL Server con Docker

El repositorio del Backend incluye un archivo docker-compose.yml preconfigurado con SQL Server 2022. Esta es la forma recomendada de ejecutar la base de datos en desarrollo.

El contenedor está configurado con los siguientes parámetros:

docker-compose.yml db:
  image: mcr.microsoft.com/mssql/server:2022-latest
  # VITAL para Mac M4: fuerza emulación para evitar errores de arquitectura
  platform: linux/amd64
  container_name: CRUDGA_DB
  restart: always
  environment:
    - ACCEPT_EULA=Y
    - MSSQL_SA_PASSWORD=${DB_PASSWORD}
    - MSSQL_PID=Developer
  ports:
    - "1433:1433"
  volumes:
    - ./mssql-data:/var/opt/mssql/data
  mem_limit: 2g
⚠️
Configurar el archivo .env antes de levantar Docker

El docker-compose.yml lee la contraseña desde la variable DB_PASSWORD del archivo .env. Si el archivo no existe o la contraseña no cumple los requisitos de SQL Server, el contenedor no arrancará correctamente. Ver Sección 4.2.

4.2 Variables de Entorno del Backend (.env)

El Backend incluye un archivo de ejemplo .env.example. Debes copiarlo y completarlo con tus valores antes de cualquier otro paso.

  • Copiar el archivo de ejemplo

    Desde la raíz del repositorio del Backend, ejecuta:

Terminal — Directorio del Backend cp .env.example .env
  • Editar el archivo .env

    Abre el archivo .env con tu editor de código y completa las variables:

.env — Backend # ── Base de Datos ────────────────────────────────────
DB_HOST=localhost
DB_PORT=1433
DB_NAME=CRUDGA_DB
DB_USER=sa
DB_PASSWORD=TuContraseñaSegura123!

# ── Aplicación ───────────────────────────────────────
PORT=3000
NODE_ENV=development
🔴
Requisitos de contraseña de SQL Server

La contraseña en DB_PASSWORD debe tener al menos 8 caracteres e incluir: mayúsculas, minúsculas, números y un carácter especial (ej: !, @, #). SQL Server rechazará contraseñas débiles y el contenedor no iniciará.

4.3 Levantar el Contenedor y Crear la Base de Datos

  • Iniciar el contenedor de SQL Server

    Desde la raíz del repositorio del Backend (donde está el docker-compose.yml):

Terminal — Directorio del Backend docker compose up -d

# Verificar que el contenedor está corriendo:
docker ps
CONTAINER ID IMAGE STATUS PORTS
xxxxxxxxxxxx mcr.microsoft.com/mssql/... Up 30 seconds 0.0.0.0:1433->1433/tcp
  • Esperar a que SQL Server inicie completamente

    El motor de SQL Server tarda entre 20 y 40 segundos en estar listo. Puedes ver los logs con docker logs CRUDGA_DB. Cuando aparezca el mensaje "SQL Server is now ready for client connections", continúa.

  • Crear la base de datos

    Conéctate con DataGrip (ver Sección 4.4) o cualquier cliente SQL y ejecuta:

SQL — Crear Base de Datos CREATE DATABASE CRUDGA_DB;

4.4 Conectar con DataGrip

  • Crear nueva fuente de datos

    En DataGrip → panel Database → clic en + → Data Source → Microsoft SQL Server.

  • Completar los datos de conexión

    Usa los mismos valores que configuraste en el archivo .env:

CampoValor
Hostlocalhost
Port1433
Usersa
PasswordEl valor de DB_PASSWORD en tu .env
DatabaseCRUDGA_DB (tras crearla)
  • Descargar el driver y probar la conexión

    DataGrip te pedirá descargar el driver de Microsoft SQL Server. Acepta. Luego haz clic en "Test Connection". Debe aparecer el mensaje en verde "Successful".

4.5 Opción Alternativa: SQL Server Local (sin Docker)

Si ya tienes SQL Server instalado directamente en tu sistema (Express o Developer Edition), puedes usarlo en lugar del contenedor Docker.

ℹ️
Requisitos para la opción sin Docker

El servicio SQL Server debe estar corriendo en el puerto 1433. El usuario sa debe estar habilitado con la misma contraseña definida en el archivo .env. La autenticación mixta (SQL + Windows) debe estar activada.

5. Instalación del Backend (NestJS)

API REST con NestJS sobre Node.js · Configuración y arranque

⚠️
Prerrequisito

Antes de continuar, asegúrate de haber completado la Sección 3 (Node.js instalado) y la Sección 4 (contenedor Docker corriendo y base de datos CRUDGA_DB creada).

5.1 Clonar el Repositorio del Backend

Terminal # Clonar el repositorio del Backend en tu directorio de trabajo
git clone <URL_REPOSITORIO_BACKEND>
cd <nombre-del-directorio-backend>

5.2 Instalar Dependencias

Terminal — Directorio del Backend # Instalar todas las dependencias de Node.js
npm install

# El proceso puede tardar 1-3 minutos en la primera instalación

5.3 Configurar Variables de Entorno

Si aún no has configurado el archivo .env, hazlo ahora siguiendo los pasos de la Sección 4.2. Este paso es obligatorio antes de iniciar el servidor.

Terminal — Directorio del Backend # Copiar el archivo de ejemplo (si no lo has hecho)
cp .env.example .env

# Abre .env con tu editor y completa los valores
# (ver Sección 4.2 para los campos requeridos)

5.4 Ejecutar en Modo Desarrollo

Terminal — Directorio del Backend # Iniciar el servidor en modo desarrollo con hot-reload
npm run start:dev

# Salida esperada en consola:
[Nest] LOG [NestApplication] Nest application successfully started
[Nest] LOG Application is running on: http://localhost:3000
ℹ️
Hot-Reload activado

En modo desarrollo (start:dev), NestJS usa Webpack Watch para recompilar automáticamente cada vez que guardas un archivo TypeScript. No es necesario reiniciar el servidor manualmente durante el desarrollo.

5.5 Verificar que la API Está Funcionando

Abre tu navegador o usa una herramienta como Postman para confirmar que el Backend responde correctamente.

Verificación en navegador o curl # Abre en el navegador:
http://localhost:3000

# O desde la terminal:
curl http://localhost:3000

# Respuesta esperada (varía según el endpoint raíz configurado):
{"status":"ok","message":"CRUDGA API running"}

Otros Comandos del Backend

ComandoDescripción
npm run start Inicia el servidor en modo producción (sin hot-reload)
npm run start:dev Modo desarrollo con hot-reload (uso habitual)

6. Instalación del Frontend (Angular)

Angular 21 + TailwindCSS + DaisyUI · Configuración y arranque

⚠️
Prerrequisito

El Backend debe estar corriendo en http://localhost:3000 antes de iniciar el Frontend. De lo contrario, las peticiones HTTP de la aplicación fallarán al cargar datos.

6.1 Clonar el Repositorio del Frontend

Terminal # Clonar el repositorio del Frontend (en un directorio distinto al Backend)
git clone <URL_REPOSITORIO_FRONTEND>
cd CRUDGA

6.2 Instalar Angular CLI (Global)

Angular CLI es la herramienta de línea de comandos oficial para crear, compilar y servir aplicaciones Angular. Solo necesitas instalarlo una vez a nivel global en tu sistema.

Terminal — Instalar Angular CLI globalmente # Instalar la versión 21 de Angular CLI
npm install -g @angular/cli@21

# Verificar la instalación
ng version
Angular CLI: 21.x.x
Node: 20.x.x
Package Manager: npm 11.x.x

6.3 Instalar Dependencias del Proyecto

Terminal — Directorio del Frontend (CRUDGA/) # Instalar todas las dependencias del proyecto
npm install

# Dependencias instaladas incluyen:
# - @angular/core, forms, router, common (^21.1.0)
# - tailwindcss (^4.1.18)
# - daisyui (^5.5.14)
# - rxjs (~7.8.0)
# - chart.js (^4.5.1)

6.4 Configuración: URL del Backend

El Frontend necesita conocer la dirección del Backend para enviar peticiones HTTP. Esta configuración generalmente se encuentra en los archivos de entorno de Angular.

src/environments/environment.ts — Configuración típica export const environment = {
  production: false,
  apiUrl: 'http://localhost:3000'
};
ℹ️
Configuración por defecto

La URL http://localhost:3000 es la configuración estándar para desarrollo local. Si el Backend corre en otro puerto o host, actualiza el valor de apiUrl antes de iniciar el Frontend.

7. Orden de Arranque del Sistema

Secuencia correcta para iniciar el entorno de desarrollo cada día

Una vez que todo el sistema está instalado, el orden de arranque para el trabajo diario es el siguiente. Respeta la secuencia para evitar errores de conexión.

  • Iniciar Docker Desktop

    Abre la aplicación Docker Desktop y espera a que el ícono de la ballena indique que el daemon está corriendo. Sin este paso, el contenedor de SQL Server no puede iniciarse.

  • Levantar el contenedor de la Base de Datos

    Desde el directorio del Backend, en la terminal:

Terminal — Directorio Backend docker compose up -d
# Verifica que el contenedor CRUDGA_DB aparezca como "Up"
docker ps
  • Iniciar el Backend (NestJS)

    Desde el directorio del Backend, en una terminal nueva:

Terminal — Directorio Backend npm run start:dev
# Espera hasta ver: "Nest application successfully started"
# El Backend queda disponible en http://localhost:3000
  • Iniciar el Frontend (Angular)

    Desde el directorio del Frontend, en otra terminal nueva:

Terminal — Directorio Frontend npm start
# El Frontend queda disponible en http://localhost:4200
  • Abrir el sistema en el navegador

    Navega a http://localhost:4200. Si todos los servicios están activos, la pantalla de inicio de sesión del Sistema de Asignaciones debe cargar correctamente.

✅
Sistema completamente operativo

Cuando los tres servicios están activos, tienes 3 terminales abiertas: una con el Backend corriendo, una con el Frontend corriendo, y Docker Desktop en segundo plano con el contenedor SQL Server. Este es el estado normal de trabajo.

8. Solución de Problemas Comunes

Errores frecuentes y cómo resolverlos paso a paso

8.1 El contenedor Docker no inicia

🔴 Error Crítico

Síntoma: docker compose up -d falla o el contenedor entra en estado Exit 1 inmediatamente.

Causa PosibleSolución
Contraseña débil en DB_PASSWORD La contraseña debe tener 8+ caracteres, mayúsculas, minúsculas, número y carácter especial
Archivo .env no existe Ejecutar cp .env.example .env y completar los valores
Puerto 1433 ocupado por otro proceso Verificar con lsof -i :1433 (Mac/Linux) y detener el proceso conflictivo
Docker Desktop no está corriendo Abrir Docker Desktop y esperar a que el daemon inicie por completo
Memoria insuficiente asignada a Docker En Docker Desktop → Settings → Resources → Memory: asignar mínimo 4 GB
Diagnóstico — Ver logs del contenedor docker logs CRUDGA_DB
# Busca mensajes de error en la salida

8.2 El Backend no conecta a la base de datos

⚠️ Error de Conexión

Síntoma: Al iniciar npm run start:dev, aparecen errores de conexión a la base de datos o la API no responde en el puerto 3000.

Causa PosibleSolución
Contenedor Docker no está corriendo Ejecutar docker compose up -d antes de iniciar el Backend
Base de datos CRUDGA_DB no fue creada Conectarse con DataGrip y ejecutar CREATE DATABASE CRUDGA_DB;
Credenciales incorrectas en el .env Verificar que DB_PASSWORD en .env coincide con la del contenedor Docker
SQL Server aún no terminó de iniciar Esperar 30-40 segundos más después de docker compose up -d

8.3 El Frontend no carga datos

⚠️ Error de Comunicación

Síntoma: La aplicación Angular abre en el navegador pero las listas aparecen vacías o hay errores de red en la consola del navegador (F12).

Causa PosibleSolución
Backend no está corriendo Verificar que npm run start:dev está activo en la terminal del Backend
URL del Backend incorrecta Revisar que apiUrl en environment.ts apunta a http://localhost:3000
Error CORS en la API Verificar que el Backend tiene CORS habilitado para el origen http://localhost:4200

8.4 Error de versión de Node.js

ℹ️ Compatibilidad

Síntoma: npm install falla con errores sobre versión de Node.js incompatible.

Solución — Actualizar Node.js con nvm # Verificar versión actual
node --version

# Instalar y usar la versión LTS si es inferior a 18
nvm install --lts
nvm use --lts

# Repetir la instalación de dependencias
npm install

8.5 Error al instalar en Mac Apple Silicon

🍎 Apple Silicon

Síntoma: Errores relacionados con arquitectura arm64 al construir el contenedor Docker.

✅
Ya está resuelto en el proyecto

11. Sistema de Autenticación y Seguridad

JWT · AuthService con Signals · Guards de ruta · Interceptor HTTP

11.1 Flujo de Autenticación JWT

FLUJO COMPLETO # 1. El usuario ingresa email y contraseña en LoginPage
# 2. AuthService.login() hace POST /api/auth/login
# 3. El backend responde con { user, token }
# 4. handleLoginSuccess() guarda el token en localStorage
# 5. Los signals _user, _token y _authStatus se actualizan
# 6. El Router navega a /areas (ruta protegida)
# 7. authInterceptor adjunta el token en cada petición HTTP
# 8. Al recargar la página: checkStatus() valida el token con /api/auth/check-status

11.2 AuthService — Estado con Signals

El servicio de autenticación usa tres signals privados para gestionar el estado de la sesión. Los signals públicos son de solo lectura (computed).

SignalTipoDescripción
_authStatus signal<AuthStatus> Estado interno: 'checking' | 'authenticated' | 'not-authenticated'
_user signal<User | null> Datos del usuario autenticado actualmente
_token signal<string | null> Token JWT almacenado en localStorage
authStatus computed() Estado público derivado — consumido por los guards
user computed() Usuario público de solo lectura
token computed() Token público de solo lectura — consumido por el interceptor
checkstatusResource rxResource() Verifica el token con el backend al iniciar la aplicación

11.3 Guards de Ruta

IsAdminGuard — Protege rutas autenticadas

Implementado como CanMatchFn funcional. Evalúa el authStatus del AuthService de forma síncrona cuando el estado ya está resuelto, o de forma asíncrona (Observable) cuando la app está arrancando con un token en localStorage.

Estado del authResultado del guard
'authenticated'Retorna true de forma síncrona — acceso permitido
'not-authenticated'Retorna false + redirige a /auth/login
'checking'Retorna un Observable que espera a que checkStatus() resuelva
Servidor (SSR)Retorna true siempre — el cliente validará después
ℹ️
Por qué CanMatch y no CanActivate

canMatch evalúa el guard antes de cargar el componente con lazy loading, evitando que el chunk de JavaScript se descargue si el usuario no está autorizado. El proyecto usa canActivate con IsAdminGuard sobre el bloque de rutas protegidas, y canMatch con NotAuthenticatedGuard en el bloque de auth.

NotAuthenticatedGuard — Protege rutas públicas

Impide que un usuario ya autenticado acceda a /auth/login o /auth/register. Si el usuario tiene sesión activa, lo redirige a la ruta principal.

11.4 Interceptor HTTP — authInterceptor

Interceptor funcional que adjunta automáticamente el token JWT a todas las peticiones salientes de la aplicación mediante la cabecera Authorization: Bearer <token>.

src/app/auth/interceptors/auth.interceptor.ts export function authInterceptor(req, next) {
  // Obtiene el token desde AuthService vía inject()
  const authToken = inject(AuthService).token();
  // Clona la request y agrega la cabecera Authorization
  const newReq = req.clone({
    headers: req.headers.append('Authorization', `Bearer ${authToken}`)
  });
  return next(newReq);
}
⚠️
Inyección con inject() dentro de funciones

Los interceptores funcionales permiten usar inject() directamente en el cuerpo de la función (no en el constructor), eliminando la necesidad de clases y evitando dependencias circulares (NG0200).

13.3 Patrón de Estado Reactivo

El patrón de estado de los servicios CRUD sigue la misma estructura en todos los módulos, garantizando coherencia y previsibilidad.

Patrón aplicado en todos los servicios CRUD # Estado de datos
entidades = signal<Entidad[]>([]) # Lista principal
selectedEntidad = signal<Entidad | null>(null) # Ítem en edición

# Estado de operaciones
isSuccess = signal<boolean>(false) # Operación exitosa
isError = signal<boolean>(false) # Error en operación

# Actualización optimista (sin recargar desde el servidor)
# Al crear: entidades.update(list => [...list, nuevo])
# Al editar: entidades.update(list => list.map(e => e.id === id ? editado : e))
# Al borrar: entidades.update(list => list.filter(e => e.id !== id))
💡
Actualización optimista sin reload

Los servicios actualizan el signal local inmediatamente tras una operación exitosa sin recargar los datos desde el servidor. Esto garantiza una interfaz instantánea y reduce la carga de red.
